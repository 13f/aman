### 🎯 R9 关注点 1：排水阶段超时与 Tool 自身超时的优先级和交互未定义（🟡 中）

**场景**：
§2.5.3 Phase 4.5 排水阶段定义了 `drain_timeout_sec: 30`。同时 §7.3 Tool 声明中定义了独立的 Tool 超时（如 `timeout: 120s`）。**两个超时机制独立作用，但排水阶段可能在 Tool 自身超时之前强制终止它。**

```
时间线：
  t=0:  Shutdown 信号到达，Phase 4.5 排水开始
  t=0:  Pipeline Step 3 正在执行 Tool "ocr-engine"（timeout: 120s，剩余 80s）
  t=30: Phase 4.5 排水超时 → **Tool 被强制终止**
  
  Tool 自身超时 (120s) 本应在 t=90 触发 → 被排水提前截断在 t=30
```

**💥 可能后果**：
- Tool 的 **Step 6（清理 → 释放临时资源）**在强制终止时可能未被调用——§7.3 工具执行流程（lines 1208-1212）的最后一步是清理，但排水强制终止可能跳过它
- Tool 自身超时的内部清理逻辑 vs 排水终止的框架级清理：两种清理路径不同，Tool 作者只能实现一种
- 如果 Tool 被排水终止时正在写入文件 → 残留临时文件；如果正在调用外部 API → API 已调用但 Tool 以为未完成
- 对比文档边界描述（lines 118-122）：`关闭中断的 Pipeline 不会被自动恢复 + 依赖 Tool 层幂等性`——但 Tool 层的幂等性不能保证清理逻辑被执行

**🛠 建议**：
- 在排水阶段描述中明确：**排水超时终止 Tool 时，框架应确保 Tool Runner 的清理步骤（§7.3 Step 6）被执行**，无论终止原因
- 或增加排水超时与 Tool 超时的交互规则：

```
排水超时与 Tool 超时的交互：
  - 排水超时独立于 Tool 超时工作，两者取其先
  - 如果 Tool 的 timeout < drain_timeout_sec：Tool 自身超时先触发，执行 Tool 层的清理逻辑
  - 如果 Tool 的 timeout > drain_timeout_sec：排水超时先触发，框架强制终止 Tool 并执行 Tool Runner 的 Step 6 清理
  - 无论哪种方式，Tool Runner 的 Step 6（清理 → 释放临时资源）必须执行
```

### 🎯 R9 关注点 2：WAL 恢复缓冲区“断点偏移量”的持久化方式未定义（🟢 低）

**场景**：
§2.5.1 WAL 缓冲约束（line 84）：

```
未读取的事件记录断点偏移量，下次启动时从断点继续重放
```

断点偏移量保存在哪里？没有定义。

| 存储位置 | 问题 |
|---------|------|
| **内存中** | Phase 1 完成后断点就在内存，但崩溃后丢失 → 下次启动从头重放 |
| **WAL 头部** | 需要修改 WAL 文件格式，Phase 1 时 WAL 可能不可写 |
| **单独的状态文件** | 需要定义 path、写入时机（每次 checkpoint？）、崩溃恢复时的校验 |
| **State Store** | Phase 1 时 State Store 可能还未初始化 |

**💥 可能后果**：
- 如果断点保存在内存中：缓冲区超限 → WAL 暂停 → Phase 1 标记"部分完成"→ 但崩溃后断点丢失 → 下次启动 WAL 从头重放（缓冲区再次超限 → 递归问题）
- 如果断点未持久化：重放暂停的实际效果为零——只是延迟了 OOM 到下一次启动

**🛠 建议**：
- 在 §2.5.1 的约束段中指定断点持久化方式：

```
WAL 恢复断点持久化：
  - 断点偏移量保存在 WAL 所在目录的独立状态文件：`{wal_path}/replay_checkpoint`
  - 每次缓冲区满暂停时，同步写入偏移量（fsync 确认）
  - Phase 1 启动时：先读取 replay_checkpoint → 从该偏移量开始重放
  - 如果 replay_checkpoint 不存在或损坏 → 从 WAL 头部（即 checkpoint 记录的偏移量）开始重放
  - Phase 2 完成后（缓冲区成功注入 Event Bus）→ 删除 replay_checkpoint 文件
```

- 风险清单新增 #48 项

### 🎯 R9 关注点 3：排水阶段“待重试队列停止重试模式”与已调度重试的竞态（🟢 低）

**场景**：
§2.5.3 Phase 4.5 最后一条（line 111）：

```
└── 待重试队列进入停止重试模式
```

待重试队列的调度模式是 WAL→内存投递失败后的指数退避重试（100ms → 500ms → 2s）。当 Phase 4.5 进入时：
- 队列中可能已有已调度（scheduled）但尚未执行的重试
- 也可能有正在执行中的重试（Tool 已被调用但未返回）

**💥 可能后果**：
- 已调度重试在排水期间触发 → 在"停止重试模式"中启动新的 Tool 执行 → 与排水等待冲突（排水在等 inflight 结束，但新重试又开始了）
- 或者：停止重试模式简单地将所有已调度重试取消 → 被取消的重试事件丢失（但 AT_LEAST_ONCE 承诺"绝不静默丢弃"）
- 或者：停止重试模式允许当前调度完成但不调度新的 → 已调度重试正常执行，属于预期的 inflight 工作

**🛠 建议**：
- 在排水阶段描述中增加子语义：

```
停止重试模式的具体行为：
  - 允许已调度但尚未执行的重试**继续执行**（属于 inflight 工作，由排水等待覆盖）
  - 不产生新的重试调度
  - 排水超时后，队列中所有**未执行**的重试事件标记为"shutdown_abandoned"
    - 在重启后的启动序列中（Phase 1 待重试队列重建时）重新入队列
    - 不静默丢弃，符合 AT_LEAST_ONCE 原则
```

- 风险清单新增 #49 项

## 最终评价

**R8 的全部 3 个问题已被认真修复。** 三个问题的修复都很到位：
- Phase 4.5 排水阶段的 5 条子步骤覆盖了通知→等待→补偿→超时→记录→终止全流程
- WAL 缓冲区约束从"存在缓冲区"细化到"最大 5000 + 超限暂停 + 断点 + 下次继续 + Phase 2 超时告警"
- dedup_key 性能指引用注释方式嵌入 Event 定义，AT_MOST_ONCE 跳过 hash 是框架实现级别的优化

R9 发现的 3 个问题集中在**新机制的实现粒度**——不是功能缺失，而是"机制已经定义，但实现者还需要知道的细节未定义"：

- **#1 号（排水 vs Tool 超时）**是两个超时机制的优先级冲突——排水 30s 和 Tool 120s，谁先触发？Tool 被强制终止时 Step 6 清理跑不跑？不同的超时命中方式导致不同的清理路径。
- **#2 号（断点持久化）**是 "记录断点偏移量" 这句话只有 5 个词，但实现者需要知道：存哪里？怎么存？崩溃了怎么办？和已有 WAL checkpoint 的关系是什么？
- **#3 号（停止重试模式语义）**是 "停止重试" 四个字的粒度问题——已调度的重试怎么办？未执行的怎么办？
