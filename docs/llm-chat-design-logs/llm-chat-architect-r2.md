## 新增内容亮点

**§13 测试架构** 是全场最大提升。6 个子节从测试层级到具体测试场景到基础设施全部覆盖：
- Property-based testing 覆盖状态转移表的合法/非法路径，不变性断言细化到 session_id、trace_id、CLOSED 终态
- 并发队列测试 4 个场景穷举了串行化、并行、溢出、清空
- WAL 重放集成测试含 3 个场景（正常启动/崩溃恢复/CLOSED 跳过），at-most-once 副作用 + at-least-once WAL 消费的语义正确
- 测试基础设施 4 个组件（MockLLMProvider / FakeEventBus / VirtualFrontend / DeterministicClock）覆盖面全

**§14 可观测性架构** 质量同样高：
- RED 指标覆盖 LLM 调用、会话队列、安全验证、基础设施、IPC 命令、前端性能 6 个领域
- Trace 传播路径图画出 MESSAGE_RECEIVED → InputSanitizer → Dispatcher → Queue → LLM Skill → Tool Calling → OutputValidator → Frontend 的完整链路
- 跨 WAL 重放的 trace_id 延续策略清晰
- 日志结构化字段规范有 replay 标记，可直接用于区分重放流量
- 告警规则含 10 条，覆盖 PagerDuty + Slack 双通道

**§15 历史裁剪策略** 解决了 R1 最棘手的 gap：
- FIFO / Weighted 两种策略的算法伪代码可直接实现
- WAL / State Store / 前端的一致性三角明确：裁剪是逻辑操作，物理保留 WAL，State Store 存裁剪后子集，前端通过 trim_info 恢复灰化标记
- §15.2 的未解决问题 #5（重启后灰化丢失）已修复——`GET /session/{id}/state` 增加可选 `trim_info` 字段

## 剩余问题（次要，不阻塞开工）

### 建议 1：Phase 3 项目数膨胀（14 项）

v2.0 的 Phase 3 从 11 项增长到 14 项，部分原因是 R1 补丁内容（限流、排水、裁剪、WAL 持久化）被后移到 Phase 3。而 Phase 2 新增的测试基础设施（3d）和可观测埋点（1d）是正确的前移决策。

但如果 Phase 3 "灵活排期"意味着可能在 Phase 2 上线后 2-4 周才开始，那么以下 3 项建议前移到 Phase 2：
- **限流模型实现**（§4.5）— 无上限的消息注入会让 Phase 2 的并发队列承受不可预测的压力。至少实现用户级 10/min 限流
- **WAL 持久化 + 断线重连**（§9.1-9.2）— 没有 WAL 的 Phase 2 意味着 Agent 重启后所有会话丢失，线上试用的用户感受会非常差
- **Phase 4.5 排水逻辑**（§9.4）— 仅在热加载/卸载场景需要，但如果 Phase 2 期间不涉及插件热更新，可留在 Phase 3

### 建议 2：基础设施错误恢复缺失

文档现有错误处理聚焦于用户可见层（§11.7 的异常场景表）。但以下基础设施级故障场景没有任何恢复策略：

| 故障 | 当前覆盖 | 缺失 |
|------|---------|------|
| WAL 写入失败（磁盘满/权限） | §13.4 测试了 WAL 重放，§14.2 有 `wal.disk_usage_percent` | 写入失败时 Agent 的降级行为？拒绝新消息？WAL 写入失败是否应阻止 MESSAGE_RECEIVED 进入 Event Bus？ |
| State Store 写入失败 | §3.4 提到 State Store 持久化 | 写入失败时会话状态回滚？重试？降级到仅内存？ |
| Event Bus 不可用 | §4.2 背压协调 | Bus 完全挂掉（非背压，不可恢复）时的行为？ |

目前 §18 边界情况表没有覆盖基础设施故障。考虑到 aman 已有 Event Bus 5 级背压和 WAL 机制，这些可能在 aman 的总体架构中有处理。建议至少在 §18.1 风险表中加一条 "LLM 特有基础设施故障的降级策略" 或在 §14.6 告警规则中补充恢复 runbook 引用。

### 建议 3：§11.8 上下文窗口管理与 §15 历史裁剪有语义重叠

§11.8 定义了 context_window 计算公式和触发条件，§15 又定义了完整的裁剪策略。两者的关系是：§11.8 定义"何时裁剪"，§15 定义"如何裁剪"。但当前 §11.8 仅有 18 行的 2 个段落，§15 有 6 个子节——不成比例。

建议：
- 将 §11.8 合并到 §15.2（触发时机）中，避免读者在两处寻找相关信息
- 或保留 §11.8 作为"上下文窗口计算"，在其中明确引用 §15 为裁剪执行策略
