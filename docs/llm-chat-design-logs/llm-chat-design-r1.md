## 发现

### 🎯 关注点 1: Workflow 状态机缺少 ERROR 态和断态恢复（🔴）

**场景**：用户发起一个长时间 LLM 调用（如 GPT-4 分析大文件），LLM Provider 返回 500 错误，或网络中断 15 秒。

**💥 可能后果**：
- 当前状态机中 PROCESSING 态的出口只有 → IDLE（发生在 `LLM_REPLY_READY`）。Provider 异常时，没有 `LLM_REPLY_READY` 到达 → **PROCESSING 永久滞留**，会话卡死
- 没有 `PROCESSING → TIMEOUT` 或 `PROCESSING → ERROR` 的转移 → 用户既无法重试也无法关闭（/session close 事件来自用户，但 Workflow 在 PROCESSING 态没有响应 SESSION_END 的转移）
- 最终的 `ACTIVE` 初始态也没有到 TIMEOUT 或 CLOSED 的出口 — 创建会话后不发送消息，会话永远不会进入终态

**🛠 建议**：
- 添加状态：`ERROR`（Provider/Tool 失败）、`RETRYING`（重试中）
- 添加转移：
  - `PROCESSING → ERROR`（Provider 异常 / Token 耗尽 / 超时）
  - `ERROR → RETRYING`（/retry 命令到达）
  - `RETRYING → PROCESSING`（重试启动）
  - `RETRYING → ERROR`（重试失败）
  - `ACTIVE → TIMEOUT`（空闲超时）
  - `PROCESSING → TIMEOUT`（LLM 响应超时）
- 每个终态需要一条补偿路径：不能只依赖用户主动操作

---

### 🎯 关注点 2: 并发消息冲突 — 同源保序与 Tool Calling 循环的竞态（🔴）

**场景**：用户连续发送两条消息"帮我查北京天气"和"顺便查一下上海的"。第一条消息触发 `tool_call(get_weather)` → LLM 等待 Tool 返回 → 第二条消息到达 Event Bus 并被 LLM Skill 处理。

**💥 可能后果**：
- §4 定义的 LLM Skill 是单事件处理器，但文档没有说明 **第二个 MESSAGE_RECEIVED 到达时，第一个是否仍在处理中**。三种可能性均未定义：
  - **覆盖**：第二条中断第一条的处理，Tool 结果返回后上下文错乱
  - **排队**：第二条排队等待，但第一条的 Tool Calling 循环产生多次 LLM 调用，排队深度不可控
  - **交错**：两条消息的 Tool 调用并行执行，写入同一 State Store 位置 → 历史数据覆盖
- §13 说"同源保序"（同一用户按顺序处理），但如果第一条的 Tool Calling 产生 3 次 LLM 调用，第二条在 Event Bus 队列中等待，用户的体验是"无响应"（消息已发送但迟迟不回）

**🛠 建议**：
- 明确 LLM Skill 的并发策略：**每条会话串行**（session-level lock），跨会话并行
- 当处理第一条消息时，第二条 MESSAGE_RECEIVED 应进入**会话级等待队列**（不是全局 Event Bus），并在第一条完成后自动处理
- 在 §14.8 的"输入框不应该等待上一条回复完成"与后端串行策略之间增加**页面端等待指示**：消息已入队，position in queue: N

### 🎯 关注点 3: /edit 命令的历史篡改 — 下游状态未定义失效（🔴）

**场景**：用户发送"帮我查北京天气"→ Agent 回复"22℃，晴"→ 用户说"为什么冬天还这么热"→ Agent 回复"北京冬季..."→ 用户返回编辑第一条消息改为"帮我查东京天气"→ 重新提交。

**💥 可能后果**：
- §14.11 将 `/edit <message_id>` 定义为"编辑上一条用户消息，重新提交"，但：
  - 会话历史中的后续所有回复（北京的 Agent 回复 + 对话后续）**语义失效**——它们基于旧消息生成
  - LLM Skill 在读历史时，会看到"东京天气"后面的回复是"冬季..."——语境完全错乱
  - 下游导出 / 审计日志中出现语义矛盾的交互单元（编辑后的消息 + 未编辑的下游回复）
  - 不知道是**替换**（删除旧消息，插入新消息）还是**追加**（保留旧消息 + 追加修正版）——两种方式对历史一致性影响完全不同

**🛠 建议**：
- 定义 /edit 的精确语义：是替换还是分支？
  - **替换**：清除旧消息之后的所有后续历史，LLM 基于新消息重新生成（`MESSAGE_EDITED` → 清空历史 → 重新触发处理流程）
  - **分支**：保留旧历史，在编辑点创建一个分支会话
- 审计日志必须记录编辑事件，包含 `original_message_id`、`edited_message_id`、`timestamp`
- 页面应显式提示"编辑后将清除后续所有回复"

### 🎯 关注点 4: 流式输出与 Tool Calling 的交错渲染未定义（🟡）

**场景**：LLM 首先生成一段文本"我现在查一下北京天气..."，然后在流中间发出 `tool_call`，收到结果后继续生成文本。

**💥 可能后果**：
- §14.4 说"已经渲染过的 chunk 不应该二次变动（不可变渲染区域）"——但如果文本 chunk 已经在滚动视口上方渲染完成，中间插入了 tool_call 卡片，用户看到的是：
  ```
  我现在查一下北京天气...
  [tool_call: get_weather]  ← 插在文本 chunk 之间
  北京 22℃，晴天。
  ```
  语义上通顺，但视觉上 tool_call 打断了一段完整文本的连续性
- 更严重的情况：LLM 返回 tool_call **不附带中间文本**（直接从首个 token 就开始 tool_call）。此时页面先出现 tool_call 卡片，然后在执行结果后显示全部文本——但页面的时间线上 tool_call 在文本**之前**，用户的阅读体验是"先看到调用信息，再看到结果文本"

**🛠 建议**：
- 定义 tool_call 的**插入时机规则**：
  - 如果 tool_call 发生在流式开始时（第一个 chunk 就是 tool_call），tool_call 卡片在文本**之前**显示
  - 如果 tool_call 在文本流中间发生，分成"上半段自然文本"→ tool_call 卡片 → "下半段自然文本"
  - 文本流结束后出现的 tool_call 不应在 UI 上打断已完成的文本块
- 每个 chunk 需要携带 `position_hint`（before / middle / after_text）来指导 UI 渲染位置

### 🎯 关注点 5: 渠道断线恢复的 Event Bus 订阅生命周期缺失（🟡）

**场景**：用户通过 WebSocket 连接聊天页面，Agent 因升级重启。重启过程中 WebSocket 断开，Agent 恢复后 WebSocket 重连。

**💥 可能后果**：
- §13 说"断线重连，恢复未完成的 LLM 响应"——但：
  - 断线期间，LLM 回复可能已经完成（存储在 State Store），但**回复事件`LLM_REPLY_READY` 已经发布过且丢失**。页面没有收到，不知道有回复
  - 重连时：State Store 中有会话历史，但 Event Bus 是内存结构——断线期间发布到 Event Bus 的事件全部丢失。页面无法通过"订阅"拿到丢失的回复
  - 页面恢复机制未定义：是轮询 State Store？还是从 Workflow 实例的 data 中拉取最新状态？
- 断线期间的 MESSAGE_RECEIVED（用户发了一条消息但没有收到回复）：消息已经入 Event Bus 但被重启中断 → **消息彻底丢失**（Event Bus 不持久化未分发事件？）

**🛠 建议**：
- 定义重连恢复的**精确语义**：
  - 重连后，客户端应通过 API 请求 `GET /session/{id}/state` 获取最新状态（不是等 Event Bus 事件）
  - 断线期间的回复：从 State Store 加载最后 N 条历史，填充到消息列表
  - 断线期间用户发送的消息：如果没有在 State Store 中找到对应回复，标记为"可能丢失"，提示用户重发
- Event Bus 需要考虑持久化策略：至少未消费的 MESSAGE_RECEIVED 应该写入 WAL，否则重启即丢消息

### 🎯 关注点 6: 双重输入消毒的同路径不一致（🟡）

**场景**：用户在输入区域输入包含疑似注入内容的字符串（如系统指令注入）。

**💥 可能后果**：
- §14.8 的"发送前业务处理"说：检测到疑似注入 → "提示用户此消息可能包含敏感内容"。**然后呢？**
  - 选项 A：仍然发送（但客户端标记了，服务器端 InputSanitizer 也检查）
  - 选项 B：阻止发送
- §9.1 的 InputSanitizer 说：匹配的模式替换为 `[redacted]`
  - 如果客户端检测到注入但允许发送 → 服务器端 InputSanitizer 将其 `[redacted]` → 用户看到"此消息可能包含敏感内容"的提示，但消息仍然显示为 `[redacted]` → 用户困惑（"我的消息去哪了？"）
  - 如果客户端阻止发送 → InputSanitizer 永远不会被执行 → §9.1 的安全保护路径实际上是**冗余的**，因为客户端是 untrusted

**核心问题**：客户端预检是 UX 优化还是安全屏障？文档没有区分。如果客户端只是提示但放行，服务器端的 InputSanitizer 才是真正的屏障。如果客户端直接阻止，那提供了 false sense of security（因为客户端可被绕过）。

**🛠 建议**：
- 明确定义客户端预检的角色是"用户帮助"（减少误触）而非"安全屏障"
- 服务器端 InputSanitizer 是**唯一的**安全屏障，无论客户端是否提示，都必须完整执行
- 增加配置项 `client_side_prompt_check`：`warn_only`（默认，仅提示不阻止）/ `block`（阻止发送，但页面明示这是客户端策略，不可靠）

### 🎯 关注点 7: 会话历史裁剪触发时机与页面反馈脱节（🟡）

**场景**：用户在一个持久会话中连续对话 200 轮，上下文长度超过 LLM 的 context window（如 32K tokens）。

**💥 可能后果**：
- §14.9 说"页面显示裁剪提示 + 最早的 N 条已归档"——但裁剪的决定方是 **LLM Skill 或 Workflow 引擎**，不是页面
  - LLM Skill 在调用 Provider 前决定裁剪 → 但页面不知道这个决定
  - 页面继续显示全部历史（已发送的消息列表），但实际注入到 LLM 上下文的只有裁剪后的部分
  - 用户看到"全部历史"，但 LLM 只能看到裁剪后的 → 用户认为 LLM 应该知道早期内容，但 LLM 不知道 → **语义断裂**
  - "最早的 N 条已归档"在页面上没有视觉标识，用户无法直观看到"这条消息 LLM 已经看不到了"

**🛠 建议**：
- 增加 `HISTORY_TRIMMED` 事件：LLM Skill 在裁剪后发布该事件到 Event Bus，页面监听后对已归档消息添加视觉效果（灰化显示 + "已归档"标签）
- 定义裁剪策略的语义：
  - 裁剪策略 token-based 还是 message-count-based？
  - 裁剪后是否依然保留在 State Store 中（只影响 LLM 上下文）？
  - 用户是否可以查看"已归档"的完整内容（展开查看）？

### 🎯 关注点 8: WAITING_INPUT 悬态 — 状态机定义但无任何转移边（🟡）

**场景**：读取 §6 的 Workflow 状态定义。

**💥 可能后果**：
- `WAITING_INPUT` 被列为一个状态，但没有任何转移指向它，也没有从它出发的转移
  - WAITING_INPUT 与 IDLE 语义重复（等待用户输入）
  - 如果 implementer 按文档实现状态机，WAITING_INPUT 是一个**不可达状态** → 要么被删除，要么造成实现困惑
  - 文档未说明 WAITING_INPUT 和 IDLE 的区别

**🛠 建议**：
- 如果 WAITING_INPUT 是设计意图中的"保持连接等待"模式，应增加转移：`PROCESSING → WAITING_INPUT` 和 `WAITING_INPUT → PROCESSING`
- 如果冗余，删除 WAITING_INPUT，统一用 IDLE

### 🎯 关注点 9: 共享会话的多用户写入竞态（🟡）

**场景**：两个用户（Alice 和 Bob）共享一个 session_id，分别在桌面端和 Slack 上同时发送消息。

**💥 可能后果**：
- §14.3 定义"多渠道共享同一个 session_id"，§14.6 说"不同用户按时间戳全局排序"
  - 但 State Store 中的会话历史是**一个文件/一个 key**。两个 LLM Skill 实例可能同时加载并写入同一个 session 的历史 → **写覆盖**
  - 如果 State Store 不支持事务，Alice 的回复可能被 Bob 的回复覆盖，或两者交错写入（前半段是 Alice 的历史，后半段是 Bob 的）→ 上下文混乱
  - "按时间戳排序"是 UI 层的排序，但底层的存储写入顺序不可控

**🛠 建议**：
- 共享会话必须使用**乐观锁**（State Store version field）或**分布式锁**来保证历史写入的原子性
- 或者降级设计：每个用户在自己的 channel 上有独立的"子历史"，只在 UI 层按时间戳融合显示
- 明确共享会话的角色：是**同一个 Agent** 同时应答两个用户，还是两个用户**共享一个上下文**但 Agent 依次处理？

### 🎯 关注点 10: SOUL 热更新与 Invocation 中的 Tool Calling 循环的竞态（🟢）

**场景**：Agent 管理员在用户正在对话时热更新了 SOUL（修改了 identity 和 boundaries）。用户当前的消息触发了 LLM 调用 → 收到了 tool_call → 正在等待 Tool 返回值。

**💥 可能后果**：
- §8 说"SOUL 热更新生效时，下一次 LLM 调用自动使用新的 system prompt"
  - 当前流程是：LLM 调用①（旧 SOUL）→ tool_call → 执行 Tool → 将 Tool 结果附加到消息列表 → LLM 调用②（下一次调用）
  - 第一次 LLM 调用使用旧 SOUL → 第二次使用新 SOUL → 同一个交互单元内 system prompt 中途变化
  - 如果新 SOUL 的 boundaries 更**严格**（如移除了某个 Tool 的权限），LLM 在第二次调用时突然无法访问已经在第一次调用中被授权使用的 Tool → 错误或不完整回复
  - 如果新 SOUL 的 identity 变化（如从"程序助手"变为"数据分析师"），两次回复的风格不一致

**🛠 建议**：
- 定义 SOUL 热更新的生效边界：**仅在完整的交互单元边界**生效（一个用户消息 → 全部 Tool Calling 循环 → 最终回复），不在 Tool Calling 循环中间生效
- 或者使用"SOUL 版本快照"：LLM Skill 在处理一个 MESSAGE_RECEIVED 时，固定当前 SOUL 版本用于整个交互单元

### 🎯 关注点 11: /retry 的重放边界未定义（🟢）

**场景**：用户发送"查上周销售额"→ LLM 返回 tool_call(get_sales_data) → Tool 执行成功 → LLM 生成回复"上周销售额 125K"。用户不满意，执行 `/retry`。

**💥 可能后果**：
- `/retry` 有至少三种解释：
  1. **仅重试最后一段 LLM 文本生成**（保留之前所有历史 + tool_call + result，只重新调用 LLM）— 最快，副作用最小
  2. **重放全部处理流程**（消息→首次 LLM 调用→tool_call→Tool→最终 LLM）— 可能产生不同的 tool_call
  3. **回退到上一个用户消息**— 丢弃当前回复，回到上一条 MESSAGE_RECEIVED 刚刚处理完的状态
- 文档没有指定是哪一种。如果是②，Tool 调用可能有**副作用**（写入 DB、发送邮件）→ 重放会重复执行这些副作用
- §13 说"所有 LLM 调用和 Tool Calling 操作记录审计日志"—但 retry 产生的重复调用如何标识为"retry"而不是新的独立调用？

**🛠 建议**：
- 明确定义 retry 语义：
  - 默认：**方式①**（仅重试最后文本生成，保留 tool_call 结果不变）
  - 可配置为方式②（复杂场景），但必须要求相关 Tool 是**幂等的**
- 审计日志中 retry 产生的记录应携带 `retry_of: <original_trace_id>` 字段，关联到原始交互单元

### 🎯 关注点 12: /stop 中途中断的语义完整性未定义（🟢）

**场景**：用户点击停止按钮（或输入 /stop）时，LLM 正在生成流式回复，或 Tool 正在执行中。

**💥 可能后果**：
- §14.4 说"用户发出停止事件时，LLM_STREAM_DONE 不会到达，页面应收起光标并标记'已中断'"
  - 但 Tool Calling 场景中的"中途打断"：
    - 正在执行 Tool → 停止后 Tool 是否继续执行完？（如果 Tool 有副作用，必须执行完才能保证一致性）
    - Tool 已执行但 LLM 还未生成最终回复 → 停止后 Tool 结果是否写入历史？
  - 停止后如何标记：§14.2 的消息状态有 `interrupted`，但**整个交互单元**（输入 → 全部 tool_call → 最终回复）哪些部分标记为 interrupted？
  - 停止后用户发送新消息 → 新消息与旧上下文的衔接？旧的中断消息在历史中的位置？

**🛠 建议**：
- 定义 /stop 的精确语义：
  - **正在流式输出**：立即终止 LLM 调用，标记 LLM 回复为 `interrupted`，但**已经写入历史的 tool_call 和 tool_result 保留**
  - **正在执行 Tool**：发出 Tool 取消信号（如果 Tool 支持 cancel），标记 tool_call 为 `cancelled`；如果 Tool 不支持取消，等待执行完成但不将其结果交付给 LLM
- 中断后的会话上下文：用户可继续发送消息，中断的消息保留在历史中，标注 `interrupted`

## 优先级矩阵

```
P0（阻止上线）
  └── #1 Workflow 缺少 ERROR 态（PROCESSING 卡死永久）
  └── #2 并发消息冲突（Session 级竞态未定义）
  └── #3 /edit 历史篡改语义未定义

P1（上线前必须解决）
  └── #5 断线恢复的 Event Bus 事件丢失
  └── #6 双重输入消毒同路径不一致
  └── #7 历史裁剪与页面反馈脱节
  └── #9 共享会话多用户写入竞态

P2（beta 前建议解决）
  └── #4 流式输出与 tool_call 交错渲染
  └── #8 WAITING_INPUT 悬态
  └── #10 SOUL 热更新跨越 Tool Calling 边界

P3（持续改进）
```

## 总评

**文档成熟度**：优秀的第一版。架构思维清晰，事件驱动的定位准确，"事件终端"的概念对传统聊天 UI 的突破有说服力。§14 的页面业务逻辑设计很详尽（消息类型、状态、多渠道聚合、SOUL 感知）。

**核心风险集中在三个维度**：

1. **状态机不完整**（#1, #8）— 三个状态（ACTIVE, WAITING_INPUT, PROCESSING）的出口不全，缺少 ERROR 恢复路径。这是最危险的问题，因为它在"正常流程"下永远不会暴露，直到第一次 Provider 故障。

2. **并发语义未定义**（#2, #5, #9）— 文档假设"一个事件一个处理"的串行世界，但真实场景中：连续两条消息、共享会话多用户同时发送、断线重连期间的事件丢失，都没有防御。

3. **用户操作边界的精确性不足**（#3, #11, #12）— /edit, /retry, /stop 这三个用户操作对系统状态的影响很大，但它们的精确语义（边界条件、副作用、审计追踪）都没有定义。implementer 会各自猜测，上线后行为不一致。

**一个贯穿全文的模式**：文档定义了"有什么"（组件、事件类型、状态），但很少定义"当 X 和 Y 同时发生时谁赢"（并发）、"当 X 失败后怎么恢复"（容错）、"当用户做了 Y 后历史状态怎么变"（一致性）。这三个"当"字问题是接下来的审计重点。
