### 🎯 R7 关注点 1：启动初始化顺序未定义（🟡 中）

**场景**：
文档定义了数十个组件（Event Bus、Event Source、Plugin、Skill、Workflow、Dispatcher、Tool Runner），但未定义 Agent 启动时这些组件的初始化顺序。

```
Agent 进程启动 → ? → ? → ? → ? → POST /agent/start 就绪

涉及的组件：
  [1] Event Bus（内存/持久化）
  [2] WAL 恢复（崩溃后重放）
  [3] Event Source 注册（Timer/FileWatch/Webhook/Cron...）
  [4] 插件加载（拓扑排序 + 依赖解析）
  [5] Skill 注册（声明式/发现式/热加载）
  [6] Workflow 状态恢复（从 State Store 加载活跃实例）
  [7] Dispatcher 路由规则注册
  [8] 背压系统初始化
  [9] 控制接口（HTTP/CLI）启动
```

**竞态场景**：
1. WAL 重放先于插件加载 → 重放的事件被分配到 Pipeline/Skill，但对应的 Tool（由插件提供）尚未注册 → 事件被丢弃或进入 DLQ
2. Workflow 状态恢复先于 Dispatcher 路由注册 → Workflow 状态已加载但路由不完整 → 恢复后的状态无法接收转移事件
3. Event Source 先于 Skill 注册 → Timer/Cron 在 Skill 就绪前就开始产生事件 → 早期事件找不到处理器
4. 控制接口先于所有组件就绪 → `GET /health` 返回 healthy 但组件尚未初始化完毕

**💥 可能后果**：
- **WAL 重放 + 插件延迟加载**：服务器重启后，持久化总线上的 AT_LEAST_ONCE 事件从 WAL 重放到空的 Event Bus，但没有插件提供的 Tool 来处理 → 事件被静默丢弃或进入 DLQ → **违反 AT_LEAST_ONCE 交付保证**
- **Workflow 实例孤岛**：Workflow 状态已恢复但找不到对应的处理器 → 事件进入但转移失败 → 实例卡在当前状态
- **健康检查误报**：`GET /health` 返回 HTTP 200，但实际尚未就绪 → 负载均衡器将流量路由到未就绪的实例

**🛠 建议**：
- 在 §3 Event 层之前增加一个 **Agent 生命周期**小节，定义明确的初始化阶段序列，例如：

```
Agent 启动阶段：
  Phase 0 [基础设施]：Event Bus 初始化 → 背压系统就绪
  Phase 1 [持久化恢复]：WAL 校验 → checkpoint 加载 → 待重试队列重建
  Phase 2 [组件注册]：插件加载（拓扑序）→ Skill 注册 → Dispatcher 路由注入
  Phase 3 [状态恢复]：Workflow 实例从 State Store 加载
  Phase 4 [源激活]：Event Source 注册 → 文件监听/Timer/Cron 启动
  Phase 5 [就绪]：控制接口开放 → health endpoint 返回 ready
```

- 增加 **readiness probe** 定义：`GET /health` 在 Phase 5 之前应返回 503 Service Unavailable
- 或按阶段细化：`GET /health/ready`（所有阶段完成）vs `GET /health/live`（进程存活但不一定就绪）
- 风险清单新增 #41 项

### 🎯 R7 关注点 2：Priority 与同一来源事件保序的冲突未定义（🟡 中）

**场景**：
文档同时声明了两条规则，在特定场景下互斥。

```
规则 A（§3.3 设计决策 5，line 1601）：
  "Event Bus 保证来自同一 Event Source 的事件按产生顺序处理"

规则 B（§3.1，line 71 & §3.3，line 224）：
  "priority: HIGH | NORMAL | LOW — 用于队列调度"
  "priority_queue: // 高优先级事件先处理"
```

**冲突触发**：同一 Event Source 先后产生两个不同优先级的消息。

```
同一 Source 产生：
  t=0: NORMAL priority      → 入队列
  t=1: HIGH priority        → 入队列（或跳队列？）
```

| 策略 | 处理顺序 | 违反的规则 |
|------|---------|-----------|
| **HIGH 跳队** | 先处理 t=1 的 HIGH，再处理 t=0 的 NORMAL | 违反规则 A（同来源保序） |
| **NORMAL 保持** | 先处理 t=0 的 NORMAL，再处理 t=1 的 HIGH | 规则 B 的"高优先级先处理"在此场景中不生效 |

**💥 可能后果**：
- 选择"优先级优先"：两个文件变更事件（NORMAL 随后 HIGH），HIGH 事件先处理 → 如果 NORMAL 是"删除文件"，HIGH 是"修改文件" → **先修改后删除**，业务顺序错误
- 选择"保序优先"：优先级在相同来源内不生效 → 开发者配置 HIGH 优先级但意外无效 → 调试困难
- 文档没有给出指导，实现者可能做任意选择

**🛠 建议**：
- 在 §3.3 的"同一来源事件保序"段（line 300-302）或设计决策 5 中增加明确规则：

```
优先级与保序的权衡（⚠ 关键规则）：
  同一 Event Source 的事件：保序优先于优先级
    → 优先级仅在同来源事件之间比较不可用时生效（跨来源场景）
    → HIGH 事件不会跳过同一来源的已排队 NORMAL 事件
    → 如需突破此约束，使用不同 Event Source 发出不同优先级的消息
  跨 Event Source 的事件：优先级正常生效
    → Source A 的 HIGH 事件先于 Source B 的 NORMAL 事件处理
```

- 在设计决策 5 和 6 之外新增**决策 9：优先级与保序的冲突规则**
- 风险清单新增 #42 项

### 🎯 R7 关注点 3：补偿操作的 retry 次数在 compensation_contract 中未定义（🟢 低）

**场景**：
§3.5 补偿执行失败路径（lines 486-492）显示补偿操作会重试 3 次：

```
2. 补偿 step3 (cleanup-temp) → 失败（文件被占用，重试 3 次仍失败）
3. Pipeline 进入 COMPENSATION_FAILED（非终态）
```

但 compensation_contract（line 456）中只定义了：

```
compensation_contract: {
    idempotent: true,
    timeout_sec: 30,
    on_failure: compensation_failed
}
```

**没有定义补偿操作的 retry 次数**。图中的"重试 3 次"是硬编码默认值，还是可配置参数？如果开发者需要更保守或更激进的补偿重试策略，没有配置入口。

**💥 可能后果**：
- 补偿重试 3 次在文档中有图无参数 → 开发者以为"补偿会重试"，但不知道重试几次或如何修改
- 如果默认 3 次不可配置，对于不同的补偿操作（本地文件删除 vs 远程 API 回滚），无法差异化设置

**🛠 建议**：
- 在 compensation_contract 中增加 `compensate_retry_count: 3`（可配置，默认 3）和 `compensate_retry_backoff: "exponential"`（默认）
- 同时更新补偿执行失败路径图中的"重试 3 次"为"按补偿合同配置重试"的变量引用
- 风险清单新增 #43 项

## 最终评价

**R6 的全部 4 个问题已被认真修复**。待重试队列满的三级联锁定义（主队列→待重试队列→WAL 写入）、parallel 补偿隔离的 4 条子条件、YAML `total_retry_count` 同步、auto_retry 自动/手动模型——全部在正文中有结构化定义。六轮积累的 40 项问题全部关闭。

R7 发现的 3 个问题标志着文档进入了第七个审计层次：**系统生命周期**和**设计决策间的权衡未澄清**。

- **#1 号（启动顺序）**是文档中最后一个"全局级"缺口。组件定义得很完整，但"它们何时亮起来"没有描述。WAL 重放先于插件加载是最危险路径——这是 crash recovery 路径上的一个问题，恰好是 AT_LEAST_ONCE 交付保证的核心路径。
- **#2 号（Priority vs 保序）**不是遗漏，而是**两条主动声明的设计规则在交汇处未做权衡**。这类问题在 R1-R6 中没有出现过——之前都是"忽略的边界"或"交互盲区"，但这是**两条主动选择的设计约束之间的矛盾**。它只在同来源多优先级事件场景下露头。
- **#3 号（补偿 retry）**是图中参数与合同中参数的不一致——图承诺了重试行为，但合同没提供对应的配置入口。
