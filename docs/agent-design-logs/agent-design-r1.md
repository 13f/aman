# Agent Design Review (R1)

> 审计人：Business Logic Auditor
> 审计对象：`agent-design.md` — 事件响应式 Agent 框架设计
> 审计日期：2026-05-05

---

## 总体评价

设计文档在概念层面的架构骨架是完整的，事件驱动的哲学一致性很强（事件模型、Event Source、Dispatcher、Pipeline/Skill/Workflow 的分层清晰）。主要问题集中在**失败路径**和**数据完整性**两个维度——这两个恰恰是"上线后让你失眠"的问题。

以下按风险等级排列，先做紧急的，再做重要的。

---

## 🎯 关注点 1：事件幂等性与重复交付（🔴 高）

**场景**：持久化 Event Bus 崩溃重启后重放未确认事件，同一个 `FILE_CREATED` 事件被投递两次。Pipeline `invoice-processor` 包括：读文件 → OCR → 提取数据 → 写入数据库 → 发 Slack 通知。

**可能后果**：
- 同份文件被 OCR 两次，数据库写入两条记录，Slack 收到两条重复消息
- 如果事件是 `FILE_DELETED`，第二次重放会导致文件不存在的空指针错误
- 文档中 Event 有 `id: UUID`，但**没有任何地方定义 Event Bus 是否做去重**、去重窗口是多久、去重键是 `id` 还是 `(source, type, payload_hash)`

**建议**：
- 明确 Event Bus 的交付语义：At-most-once / At-least-once / Exactly-once？当前完全空白
- At-least-once（持久化模式的常见选择）下，定义每个 Skill/Pipeline 的**幂等契约**
- 去重不能仅依赖 UUID，必须有明确的去重时间窗口（如 "30s 内相同 source + type + payload_hash 丢弃"）

---

## 🎯 关注点 2：Pipeline 失败后的回滚黑洞（🔴 高）

**场景**：Pipeline 5 个步骤：Filter → Transform(OCR) → Action(extract-invoice-data) → Action(insert-db) → Output。步骤 3 成功并写入临时文件，步骤 4 数据库写入失败。

**可能后果**：
- 步骤 3 的临时文件成为**孤儿资源**，永远不会被清理
- 数据库无记录，外部系统（OCR 容器）已经有了状态变化，无法回滚
- 文档说"可重试"——重试 N 次仍失败，事件去哪了？**没有 Dead Letter Channel 的定义**
- 重试时步骤 1-2 可能幂等，但步骤 3 再跑一次可能产生重复临时文件

**建议**：
- 每个 Pipeline 步骤定义补偿语义：要么整体事务（Saga 模式），要么每个步骤定义 `rollback()` 钩子
- 定义 Dead Letter Channel：重试 N 次仍失败的事件写入 DLQ，而不是静默消失
- 临时资源绑定 `lifespan`：要么关联到 Event 的 TTL，要么有兜底清理守护

---

## 🎯 关注点 3：背压策略 `drop_lowest_priority` = 静默丢数据（🔴 高）

**场景**：Event Bus 满（10,000 上限），此时来了一个低优先级 `TIMER_TICK:heartbeat` 和一个低优先级 `DATA_CHANGED:ledger-entry`。心跳事件和记账数据变更被同等丢弃。

**可能后果**：
- 低优先级 ≠ 低重要性。一个"低优先级"事件可能只是业务上的非实时要求，但数据本身**不可丢**
- 没有任何机制区分"可丢事件"（metrics、heartbeat）和"不可丢事件"（审计日志、数据变更、支付回调）
- 队列满时丢弃事件——没有持久化到磁盘、没有告警通知、无法追溯丢失了哪些事件

**建议**：
- 事件模型增加 `delivery_guarantee: AT_MOST_ONCE | AT_LEAST_ONCE | EXACTLY_ONCE`，与 `priority` 正交
- 背压策略分层：AT_MOST_ONCE 事件可丢；AT_LEAST_ONCE 事件必须阻塞或溢出到磁盘
- 任何丢弃必须记入结构化日志（包含被丢弃事件的 ID、source、type、时间戳）

---

## 🎯 关注点 4：Workflow 状态机的"幽灵状态"（🟡 中）

**场景**：`approval-flow` 定义了 pending → reviewing → approved/rejected。审批流卡在 `reviewing` 状态 30 天。

**可能后果**：
- 没有超时/过期状态——工作流实例永远不会超时自动转移
- 没有错误状态——如果 `notifyUser` 回调失败，状态机停在原地，无 error/retry 路径
- `from: ANY, event: CANCEL, to: CANCELLED`——ANY 是否覆盖未初始化的状态？
- 没有完成/归档状态——已终态的工作流实例永远留在内存/存储中，随时间推移造成泄漏

**建议**：
- 每个状态机必须定义：`timeout`（在某状态的超时时间）、`error` 状态（不可恢复错误的终点）、`completed/archived`（可回收的终止状态）
- 守卫条件（`guard: hasPermission`）失败时的 fallback 状态必须定义

---

## 🎯 关注点 5：Cron 动态频率无最小间隔守卫（🟡 中）

**场景**：`adaptive-poll` 支持运行时 `reconfigure({interval: "10s"})`。配置错误或逻辑缺陷将 interval 设为 `1ms`。

**可能后果**：
- 每秒 1000 个 CRON_TICK 事件涌入 Event Bus
- 运行时 API 无权限护栏——一个低权限插件或恶意入站请求可以篡改任意 cron job 的频率
- 背压策略表现为"先挤爆队列，再丢弃其他事件"，局部问题扩散为全局故障

**建议**：
- CronSource 必须硬编码最小间隔约束（如 `min_interval: 1s`），即使上层传更小值也要 clamp
- `reconfigure` 操作应是一个需要授权的内部事件，不应是无防护的 API 端点
- 动态频率变更应有速率限制和审计日志

---

## 🎯 关注点 6：时区语义未定义（🟡 中）

**场景**：`cron_jobs: [{ schedule: "0 9 * * *", timezone: "Asia/Shanghai" }]`。系统是 UTC，某些容器镜像可能是 America/New_York。夏令时转换日（Spring Forward / Fall Back）。

**可能后果**：
- 事件 `timestamp` 没有明确参考系——是用户端的时区还是系统 UTC？
- 跨时区迁移时 cron 任务的调度参考系是什么？
- 夏令时 Spring Forward（02:00→03:00），02:30 的 cron 任务呢？Fall Back（02:00→01:00），01:00 的 cron 执行两次？
- 支持秒级精度（"6 字段"）但时区 ambiguity 没解决

**建议**：
- 强制约定：所有事件时间戳使用 UTC（Unix epoch 毫秒），仅在显示/配置层做时区转换
- Cron 调度器内部使用 UTC 计算，`timezone` 仅在"计算下次触发点"做转换
- 明确夏令时策略：跳过还是补偿？标准时间优先还是 Wall Clock 优先？

---

## 🎯 关注点 7：插件依赖无环检测与悬空依赖（🟡 中）

**场景**：Plugin A 依赖 B，Plugin B 依赖 A（循环）。或运行时 B 被 disable。

**可能后果**：
- 循环依赖：加载时死锁 / Stack Overflow
- 悬空依赖：B 被 disable 后，A 在 `on_load` 中引用的 B 的 function/skill/tool 成为空指针
- 版本声明 `>= 2.0` 无法防止 API-breaking 的 3.0 版本

**建议**：
- 加载前必须做拓扑排序 + 环检测
- 定义 disable 时的通知顺序：先通知依赖方（`on_dependency_unloading` 钩子），再卸载被依赖者
- 版本声明建议使用 SemVer 范围（如 `>=2.0 <3.0`）

---

## 🎯 关注点 8：State Store 无并发语义（🟡 中）

**场景**：Skill A 响应事件 X 写入 `state_store.key_A`，Skill B 响应事件 Y 同时写入 `state_store.key_A`。

**可能后果**：
- 写-写冲突：最后一个写者胜出，先写的数据静默丢失
- 读-写冲突：B 读到 A 写了一半的数据（缺乏事务隔离）
- 文档说"该 skill 的私有空间"——但私有空间是物理隔离还是命名空间隔离？一个 Skill 能否枚举所有 Key？

**建议**：
- 明确 State Store 的隔离级别：读已提交？可重复读？可序列化？
- 跨 Skill 共享的 key 应提供乐观锁（版本号）或悲观锁
- 定义 SKill 私有存储的权限边界（物理隔离 / 命名空间 / 访问控制）

---

## 🎯 关注点 9：已知风险章节自身的漏洞（🟡 中）

**场景**：风险表列出 5 项风险，等级有高/中，但存在系统性缺失。

**可能后果**：
- **缺少数据完整性风险**：文件刚写入到一半触发 FILE_CHANGED → Pipeline 读到不完整的文件
- **缺少配置泄露风险**：`${SLACK_TOKEN}` 通过环境变量注入——如果 Agent 进程被 dump，内存中所有敏感配置是明文
- **缺少审计缺失风险**：事件元数据是"可选"的——如果某个插件不设置 TraceID，事后无法追溯事件链路
- **风险等级无标准**：什么是"高"？影响范围大？发生概率高？修复成本高？
- **恢复目标缺失**：没有 RPO（可丢失多少数据）/ RTO（多快恢复），"从 checkpoint 恢复"无法量化验证

**建议**：
- 增加数据完整性风险：文件监听需要"稳定确认"机制（文件关闭后或 500ms 静默后触发）
- 敏感配置对标 Vault/Secret 管理方案
- TraceID 应是框架强制注入而非可选
- 定义风险定级矩阵：影响 × 概率 × 检测难度
- 定义 RPO / RTO

---

## 🎯 关注点 10：Checkpoint 恢复语义不完整（🟡 中）

**场景**：事件循环崩溃。"持久化模式下，重启后从上次 checkpoint 恢复"。但崩溃发生在事件处理到 70%、checkpoint 尚未写入的时刻。

**可能后果**：
- 未 checkpoint 的事件丢失
- 已执行 70% 的 Pipeline 的副作用（临时文件、部分数据库写入）成为孤立状态
- "多实例主备切换"——但 in_memory 模式的 Event Bus 无法共享状态，备机切换为零状态
- 主备切换时的检查清单缺失：队列偏移量、Workflow 实例快照、执行中的 Future

**建议**：
- 定义 checkpoint 写入策略：同步 vs 异步？每 N 个事件一次？
- 建议引入预写日志（WAL）模式：先持久化再处理，而不是先处理后 checkpoint
- 主备切换需同步的内容：事件队列偏移 + 全部 Workflow 状态 + 进行中的 Tool 执行

## 风险汇总矩阵

| # | 缺口 | 等级 | 触发条件 | 爆发后果 |
|---|------|------|---------|---------|
| 1 | 无事件幂等契约 | 🔴 高 | 队列重放 / 网络重传 | 重复付费 / 重复通知 / 数据重复 |
| 2 | Pipeline 失败无补偿 | 🔴 高 | 任何 Pipeline 中间步骤失败 | 孤儿资源 / 状态不一致 |
| 3 | drop_lowest_priority 丢数据 | 🔴 高 | 事件风暴 / 队列满 | 低优先级业务事件永久丢失 |
| 4 | State Machine 无超时/错误态 | 🟡 中 | 工作流卡住 / 回调失败 | 幽灵实例无限堆积 |
| 5 | 动态频率无最小间隔守卫 | 🟡 中 | 配置失误 / 恶意调用 | 自我 DDoS 级联故障 |
| 6 | 时区语义未定义 | 🟡 中 | 夏令时转换 / 跨时区移动 | 定时任务错乱或漏执行 |
| 7 | 插件依赖无环检测 | 🟡 中 | 循环依赖 / 运行时卸载 | 加载死锁 / 空指针崩溃 |

## 几个值得肯定的设计选择

审计不只是挑毛病。这几个决策做对了，值得保留：

1. **同一来源事件保序**（设计决策 5）：明确声明跨来源的事件顺序不做保证，开诚布公——这是分布式系统中诚实的设计。

2. **State Machine 作为一等公民**（设计决策 4）：在 Skill 内手搓状态机是 Bug 的温床，提升为内建模块是对的。

3. **插件隔离策略分层**（进程内 / 子进程 / 容器 / WASM）：不搞一刀切，按信任等级匹配隔离成本。

4. **已知风险章节的"循环事件"检测**：TTL + 最大传递次数是经典的防死循环手段，这个想到了。

```
  └── 实现前必须定：Pipeline 失败补偿与 DLQ（#2）

P1（上线前必须解决）
  ├── 背压策略分层（#3）
  ├── State Machine 超时/错误/归档态（#4）
  ├── 文件监听稳定性（#9 中的缺失项）
  └── TraceID 强制注入（#9 中的缺失项）

  ├── Cron 最小间隔守卫（#5）

  ├── RPO/RTO 定义 + Checkpoint 策略（#10）

```
