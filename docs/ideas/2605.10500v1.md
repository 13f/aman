- **Authors**: Genrui Zhang, Erle Zhu, Jinfeng Zhou, Caiyan Jia, Hongning Wang — Tsinghua University & Beijing Jiaotong University

## 论文核心贡献

**SkillEvolver 是一个 meta-skill** — 它本身就是一个技能，被加载到任意 CLI Agent（Claude Code、Codex 等）中，然后**迭代地创作、部署、审计、精炼领域专用技能**。

核心创新：学习目标不是模型参数，而是**技能文本和代码**，产物直接可用。

```
┌──────────────────────────────────────────────────┐
│ SkillEvolver (meta-skill, R iterations)           │
│                                                    │
│  for r = 0 .. R-1:                                │
│    1. Strategy-Diversified Exploration (K=4)      │
│       → 4 distinct strategies, 1 trial each       │
│    2. Contrastive Skill Update                    │
│       → Compare high-reward vs low-reward traces  │
│       → Surgical patch (not full rewrite)         │
│    3. Independent Audit (9 mechanical checks)     │
│       → Fresh-session Auditor, no context leak    │
│    4. Deploy v_{r+1}, repeat                      │
│                                                    │
│  Final: Select best v* validated on hold-out       │
└──────────────────────────────────────────────────┘
```

### 关键实验结果（Claude Opus 4.6 + Claude Code）

| Condition | SkillsBench Avg@5 | Δ vs No-Skill |
|---|---|---|
| No skill | 29.9% | — |
| Human-curated | 43.6% | +13.7pp |
| Self-Gen (单次生成) | 32.0% | +2.1pp |
| SkillCreator-SkillsBench | 33.9% | +4.0pp |
| **SkillEvolver R=1** | **48.2%** | **+18.3pp** |
| **SkillEvolver R=2** | **56.9%** | **+27.0pp** |

关键发现：
- R=1 已经**超过人类 curated 技能**（48.2% vs 43.6%）
- R=2 第二轮贡献了 +8.7pp，占总提升的约 **2/3**
- 成本仅 $3.92/task（R=2），比 SkillCreator 的 $6.97 便宜 ~44%
- 进化后的技能让下游 Agent 减少 19.4% token、15.3% turn、23.8% 耗时

## 四个核心机制详解

### 1. Strategy-Diversified Exploration（策略多样化的探索）

**不是随机尝试**，而是在高层设计轴上系统性地分化：

- K=4 个策略文件，每个在关键决策轴上不同（库选择、算法族、数据结构、pipeline 顺序）
- 每个策略分配到一个独立 trial
- r=0 时没有领域技能可依赖；r≥1 时当前候选技能作为真实依赖安装
- 关键洞察：**多样化来自策略空间的结构化探索，而不是同一策略的反复采样**

### 2. Contrastive Skill Update（对比式技能更新）

**不是全量重写**，而是手术式修补：

- 比较 high-reward 轨迹和 low-reward 轨迹，识别差距
- 核心过滤器：「候选特征是否可能仅从预训练中就能知道？」— 如果是，不写入技能
- 只增量添加从实际运行中发现的、非显而易见的操作知识
- 对比信号让 LLM 能定位到「哪里出了问题」而不是「重新写一遍」

### 3. Independent Audit（独立审计）

**Fresh-session Auditor**（干净上下文，不知道技能是怎么生成的）检查 9 项机制性问题：

| # | 检查项 | 类型 |
|---|---|---|
| 1 | 语法/格式有效性 | 结构 |
| 2 | 逻辑一致性 | 语义 |
| 3 | 步骤完整性 | 语义 |
| 4 | 过度拟合（硬编码路径、魔法数字） | 部署 |
| 5 | 不可验证的声明 | 部署 |
| 6 | 与已有工具/依赖的兼容性 | 部署 |
| 7 | **Silent-bypass** — 技能内容有效但运行时从不被调用 | 部署特有 |
| 8 | **Primary-action hoisting** — 关键操作被错误提升/跳过 | 部署特有 |
| 9 | **Discovery-script preservation** — 探索脚本在技能化后丢失 | 部署特有 |

Check 7–9 是论文发现的「部署时才会暴露」的新型失效模式，来自真实 case study。

### 4. Finalization（最终选择）

- 在所有迭代版本 {v₁...v_R} 中选择最优
- 在 hold-out 验证集 𝒯_val 上评估
- 不一定是最后一个版本最好 — 有时中间版本泛化性更好

## 与 MUSE-Autoskill (2605.27366v1) 的关键区别

| 维度 | MUSE-Autoskill | SkillEvolver |
|---|---|---|
| **生成方式** | 从单条成功轨迹蒸馏 | K=4 策略探索 + 对比更新 |
| **需要的 trials** | 1 条成功轨迹 | ~4 trials per task × R iterations |
| **迭代** | 无（测试失败才 refine） | R=2 迭代，第二轮贡献 +8.7pp |
| **更新方式** | 全量重写 SKILL.md | 手术式 patch（对比信号驱动） |
| **质量保障** | pytest 测试套件 | 9 项机械审计 + hold-out 验证 |
| **部署检查** | 无 | Silent-bypass / hoisting / discovery 检查 |
| **跨任务** | 无 | 无（都限于单任务） |
| **成本** | ~383K tokens/task（一次生成） | $3.92/task（R=2，含所有 trial） |

两者互补：MUSE 擅长从已有成功中蒸馏，SkillEvolver 擅长从失败中迭代改进。

## 🔥 最值得借鉴的方向

### 1. Meta-Skill 框架：把「技能创建」本身变成技能

**论文做法**：SkillEvolver 是一个 SKILL.md 文件，被加载后获得「创建/改进其他技能」的能力。

**aman 现状**：
- `formatting.rs` 已经定义了 meta-skill 概念（plan/todo/writing-plans/subagent-driven-development）
- 但这些 meta-skill 只指导 Agent **如何工作**（plan → 先探索再写计划），不是指导 Agent **如何创建技能**
- 系统提示末尾有："consider offering to save the approach as a skill"（手动、被动）

**aman 落地方案**：

新增内置 meta-skill `skill-evolver`，作为一个 SKILL.md 文件：

```markdown
# skill-evolver (meta-skill)

## 触发条件
当 Agent 遇到以下情况时，加载此技能：
- 执行了复杂任务且成功完成
- 某个操作模式重复出现 2 次以上
- 用户显式要求创建技能

## 流程

### Phase 1: 轨迹捕获
- 从当前 session history 中提取关键步骤
- 记录：输入状态 → 操作序列 → 输出状态 → 成功/失败信号

### Phase 2: 策略生成（K=3）
- 生成 3 个不同策略变体（不同工具选择、不同 pipeline 顺序）
- 每个变体是一个 SKILL.md 草稿

### Phase 3: 审计
- 9 项机械检查（语法、完整性、硬编码、可验证性等）
- 不通过的变体自动修复或丢弃

### Phase 4: 注册
- 通过审计的变体取最优，注册到 SkillRegistry
- 建议用户 review 后启用
```

**工作量**：meta-skill 主要是 SKILL.md 文本 + 少量 Rust 基础设施（轨迹捕获 API），约 ~400 行。

### 2. 轨迹捕获与对比式更新

**论文做法**：
- 保存完整 ReAct 轨迹（turn-by-turn 的 thought-action-observation）
- 对比 high-reward vs low-reward 轨迹，找出差距
- 只把「非显而易见」的操作知识写入技能

**aman 现状**：
- `ReActContext` 有 `history: Vec<ChatMessage>`，但不持久化
- `SessionHistoryStore` 存储会话历史，但不做结构化轨迹分析
- 没有 reward 信号的概念

**aman 落地方案**：

### 3. 独立技能审计器（9 Checks）

**论文做法**：Fresh-session Auditor（干净上下文）执行 9 项机械检查。

**aman 现状**：
- `kernel/eval` 有四种策略（rule/assertion/heuristic/LLM-judge），但都面向 LLM 输出评估
- 没有面向技能工件的审计

**aman 落地方案**：

```rust
// kernel/skill/src/auditor.rs (新模块)

pub struct SkillAuditor {
    eval_engine: Arc<EvalEngine>,
    checks: Vec<AuditCheck>,
}

pub struct AuditCheck {
    pub name: String,
    pub category: AuditCategory,
    pub rule: AuditRule,
}

pub enum AuditCategory {
    Structural,   // Checks 1-3: syntax, logic, completeness
    Deployment,   // Checks 4-6: overfitting, unverifiable claims, compatibility
    Runtime,      // Checks 7-9: silent-bypass, hoisting, discovery preservation
}

pub enum AuditRule {
    /// Regex/pattern-based check (zero API cost).
    Mechanical { pattern: String, severity: Severity },
    /// LLM-based semantic check.
    Semantic { prompt: String, pass_threshold: f64 },
}

impl SkillAuditor {
    pub fn audit(&self, skill: &SkillPackage) -> AuditReport {
        let mut findings = Vec::new();
        for check in &self.checks {
            findings.push(check.run(skill));
        }
        AuditReport {
            pass: findings.iter().all(|f| f.severity != Severity::Blocking),
            findings,
            pass_rate: findings.iter().filter(|f| f.passed).count() as f64 / findings.len() as f64,
        }
    }
}
```

其中 9 项检查的具体实现：
- **Check 1-3**（结构）：规则引擎即可（已有 `kernel/eval` rule-based 策略）
- **Check 4-6**（部署）：LLM-as-Judge 语义检查（已有 `kernel/eval` LLM-judge 策略）
- **Check 7-9**（运行时）：需要在真实部署环境中验证（与 sandbox 整合）

**工作量**：~400 行（审计器框架 + 9 项检查规则）

### 4. 策略模板系统

**论文做法**：K=4 个策略文件，每个在高层设计轴上不同。

**aman 落地方案**：

不需要复杂的代码框架。核心是一个**策略模板 prompt**，指导 LLM 在生成技能时从不同角度探索：

```markdown
## Strategy Template (injected into skill_create prompt)

Generate K=3 distinct skill variants by varying at least TWO of these axes:

| Axis | Options |
|---|---|
| **Library / Tool** | different library choices for the same task |
| **Algorithm Family** | different algorithmic approaches |
| **Pipeline Order** | different sequencing of steps |
| **Error Handling** | fail-fast vs graceful degradation |
| **Output Format** | structured JSON vs human-readable report |

For each variant, write:
1. Why this strategy might work (strengths)
2. Where it might fail (weaknesses)
3. Signals that would indicate it's the right choice
```

**工作量**：~100 行（prompt 模板 + 策略选择逻辑）

### 5. Iterative Refinement Loop

**论文做法**：R 轮迭代，每轮：探索 → 对�� → 审计 → 部署新版本。

**aman 现状**：
- `SkillRegistry.upsert_loaded()` 已支持版本升级
- 但没有自动触发迭代的机制

**aman 落地方案**：

```rust
// kernel/skill/src/evolver.rs (新模块)

pub struct SkillEvolver {
    auditor: SkillAuditor,
    trajectory_store: TrajectoryStore,
    llm: Arc<dyn LlmProvider>,
    max_iterations: u32,  // R=2 or R=3
}

impl SkillEvolver {
    pub async fn evolve(
        &self,
        skill_name: &str,
        task_description: &str,
        trials: usize,  // K=4
    ) -> AmanResult<EvolutionReport> {
        let mut versions: Vec<SkillVersion> = Vec::new();

        for r in 0..self.max_iterations {
            // Phase 1: Strategy-diversified exploration
            let trajectories = self.explore(skill_name, task_description, trials).await?;

            // Phase 2: Contrastive update
            let patch = self.contrast(&trajectories)?;
            let new_version = self.apply_patch(skill_name, &patch)?;

            // Phase 3: Independent audit
            let report = self.auditor.audit(&new_version);
            if report.pass_rate >= 0.75 {
                versions.push(new_version);
                break;  // Converged
            }

            versions.push(new_version);
        }

        // Phase 4: Finalization — select best version
        Ok(self.finalize(versions))
    }
}
```

**工作量**：~500 行（迭代循环 + 收敛判断 + 版本管理）

## 与上一篇论文 (MUSE-Autoskill) 的结合

两篇论文互补性很强，合在一起可以形成完整的技能进化体系：

```
MUSE-Autoskill                    SkillEvolver
─────────────────                 ─────────────────
从成功轨迹蒸馏技能      +         从失败对比中迭代改进
pytest 测试验证         +         9 项机械审计
单次生成                +         R 轮迭代
全量重写 SKILL.md       +         手术式 patch
Per-Skill Memory        +         轨迹捕获与分析
```

**组合后的 aman 技能进化流程**：

```
1. 轨迹捕获（新基建）
       ↓
2. 首次技能生成（MUSE-style 蒸馏）
       ↓
3. 测试验证（pytest + 9 checks）
       ↓
4. 部署，收集更多轨迹
       ↓
5. Per-Skill Memory 积累（2605.27366v1 的 .memory.md）
       ↓
6. 对比式迭代更新（SkillEvolver-style）
       ↓
7. 审计 + 部署新版本 → 循环
```

## 总结

SkillEvolver 的核心洞察是：**技能创建不是一次性的 LLM 蒸馏任务，而是一个需要策略探索、对比学习、独立审计的迭代搜索过程**。

与 aman 的契合点：

1. **Meta-skill 概念与 aman 高度一致** — aman 已经有 meta-skill 的分类体系和渐进式加载机制，只需要新增一个 `skill-evolver` meta-skill
2. **最大差距是轨迹基础设施** — aman 目前不捕获结构化轨迹，这是所有后续能力的 blocker，应优先建设
3. **审计器可以复用 eval 系统** — Checks 1-6 直接用现有 `kernel/eval` 的策略，Checks 7-9 是论文发现的独特 failure mode
4. **与 MUSE-Autoskill 互补而非替代** — MUSE 提供「从成功中蒸馏」，SkillEvolver 提供「从失败中迭代」，两者组合才能形成完整闭环

建议路径：**先建轨迹基础设施 → 写 skill-evolver meta-skill → 加审计器 → 做对比式更新**，与 MUSE-Autoskill 的 Per-Skill Memory 并行推进。
