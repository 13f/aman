### 🎯 R11 关注点 1：Phase 2 启动中断时，"已加载的插件"含义不明确（🟡 中）

**场景**：
§2.5.4 Phase 2 中断规则（lines 153-155）：

```
  - Phase 2 [组件注册中]：
    - 已加载的插件按反向拓扑序走卸载流程（on_unload + on_dependency_unloading）
    - 未加载的插件跳过（从未初始化，无需清理）
```

§4.3 插件生命周期（lines 986-1006）定义了三个状态：

```
发现/注册 → Loaded → Enabled → Running → Paused / Disabled / Shutdown
```

"已加载的" 在这三个状态中的边界是模糊的：

| 插件状态 | on_load 完成？ | on_unload 可用？ | 属于"已加载"？ |
|---------|---------------|-----------------|---------------|
| 拓扑排序+版本检查通过（Loaded） | ❌ 尚未执行 | ❌ 未注册 | 文档未定义 |
| on_load() 执行中（Loaded→Enabled 过渡中） | ❌ 进行中 | ❌ 未注册 | 文档未定义 |
| 资源注册完成（Enabled） | ✅ | ✅ | 应该是 |
| 正常运作（Running） | ✅ | ✅ | 应该是 |

**💥 可能后果**：
- 插件 A 在拓扑排序中通过（Loaded），正在执行 on_load()（如 `init_db()` 建立数据库连接），此时 shutdown 到达
- 规则说"已加载的走卸载流程"，调 `on_unload()` → 但 on_load() 还没完成，`on_unload` 的回调函数引用尚未注册 → **调用失败或未定义行为**
- 或者实现者将"已加载"理解为至少 Loaded → 对半加载插件调用 on_unload → on_unload 访问未初始化的内部状态 → 崩溃
- 或者实现者将"已加载"理解为至少 Enabled → 跳过 on_load 进行中的插件 → 资源泄漏（数据库连接已部分建立、文件句柄已打开）

**🛠 建议**：
- 在 §2.5.4 的 Phase 2 中断规则中精细化定义：

```
  - Phase 2 [组件注册中]：
    - **全加载的插件**（on_load 已完成，业务资源已就绪）：按反向拓扑序走卸载流程（on_unload + on_dependency_unloading）
    - **半加载的插件**（拓扑排序+版本检查已通过，但 on_load 执行中或未开始）：
      - 不调用 on_unload（函数引用尚未注册）
      - 框架负责回收已分配的基础资源（进程级内存、文件描述符——OS 会在进程退出时自动回收）
      - 记录告警日志：\"插件 X 在 on_load 阶段被中断，on_unload 跳过\"
    - 未加载的插件（尚未到达拓扑排序阶段）：跳过（从未初始化，无需清理）
```

- 或在 §4.3 插件生命周期中增加一个中间状态 `Loading`（on_load 执行中），明确其退出行为
- 风险清单新增 #52 项

### 🎯 R11 关注点 2：POST /agent/start 在 shutdown 中断期间的返回值未定义（🟢 低）

**场景**：
§9.3 控制接口定义 `POST /agent/start` 为"启动事件循环"（line 1555）。这是一个同步/阻塞调用。如果在 startup 过程中 shutdown 到达（按 §2.5.4 规则中断了启动），`POST /agent/start` 的 HTTP 响应是什么？

```
t=0:  POST /agent/start → HTTP 202 Accepted（异步？）或阻塞直到 Phase 5
t=1:  POST /agent/shutdown（另一连接）
t=2:  启动被中断（Phase 2 → 关闭序列）
t=3:  POST /agent/start 返回什么？
```

**可能性与问题**：

| 返回值 | 问题 |
|--------|------|
| HTTP 200 OK（启动成功） | 误导——Agent 实际上被关闭了 |
| HTTP 500 Internal Error | 语义含糊——是启动失败还是被中断？ |
| HTTP 409 Conflict | 需要文档定义此状态码含义 |
| 阻塞直到 shutdown 完成（然后再返回错误） | 调用者永远不知道启动被中断了 |

**💥 可能后果**：
- 编排工具（如 k8s init container）调用 start 后等待 200 → 收到 500 后认为 Agent 异常 → 重启 Pod → 再次冲突陷入循环
- 运维脚本 start → sleep → health check 的模式在中断场景下产生误报

**🛠 建议**：
- 在 §9.3 的 `POST /agent/start` 描述中增加：

```
POST /agent/start 行为补充：
  - 同步阻塞直到 Phase 5 就绪后返回 HTTP 200 OK
  - 如果启动过程中被 shutdown 中断：返回 HTTP 409 Conflict
    - 响应 body: { "status": "interrupted_by_shutdown", "phase": "初始化的阶段名" }
  - 如果启动过程中发生不可恢复错误：返回 HTTP 500 及错误详情
  - 调用者应处理 409 响应：检查 Agent 状态（GET /health）决定是否需要重新 start
```

- 风险清单新增 #53 项
