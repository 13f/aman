### 🎯 R13 关注点 1：YAML 配置示例中 check_open_files 使用 `true` 而非推荐的 `auto`（🟢 低）

**场景**：
§3.2 文档节（lines 344-347）明确定义：

```
> `check_open_files` 配置支持三值：`auto | true | false`（默认 `auto`）
> - `auto`：自动检测文件系统类型，本地 FS 启用锁检测，远程/虚拟 FS 跳过
> - `true`：强制启用（仅在确认底层 FS 支持锁检测时使用）
```

但 §9.1 YAML 完整配置示例（line 1529）中使用的是：

```yaml
      stability:
        debounce_ms: 500
        max_stable_wait_ms: 30000
        check_open_files: true
```

**💥 可能后果**：
- 开发者在远程/虚拟文件系统上部署时，复制示例中的 `check_open_files: true` 到生产配置
- 锁检测远程 FS 上不可靠 → 触发 `incomplete: true` 发布的频率增高或不发布事件
- 文档自己写了"仅在确认底层 FS 支持锁检测时使用"，但默认示例引导大家用 `true`

**🛠 建议**：
- 将 §9.1 YAML 示例中的 `check_open_files: true` 改为 `check_open_files: auto`，与文档节中的推荐默认值一致
- 风险清单新增 #56 项

### 🎯 R13 关注点 2：POST /agent/shutdown 的返回行为未定义，与 start 不对称（🟢 低）

**场景**：
§9.3 为 `POST /agent/start` 定义了三种返回值及幂等性（lines 1687-1694）。但相邻的 `POST /agent/shutdown`（line 1695）只有一行注释：

```python
POST /agent/shutdown           # 优雅关闭
```

| 属性 | /agent/start | /agent/shutdown |
|------|-------------|----------------|
| 是否阻塞直到完成 | ✅ 明确："同步阻塞直到 Phase 5" | ❌ 未定义 |
| 返回值 | ✅ 200 / 409 / 500 三种 | ❌ 未定义 |
| 幂等性 | ✅ 已运行则 200 OK | ❌ 未定义 |
| 超时 | ❌ 未定义 | ❌ 未定义 |

**💥 可能后果**：
- shutdown 可能是异步立即返回的（200 OK），也可能是同步阻塞直到关闭完成的——调用者不知道
- 编排脚本调用 shutdown 后立即 `GET /health` — 如果 shutdown 是异步的，health 可能还返回 200；如果是同步的，health 已经 503
- 如果 shutdown 已经发起但未完成，再次 POST /agent/shutdown 的行为未定义（第二次 shutdown 是忽略？返回错误？排队？）

**🛠 建议**：
- 在 §9.3 的 `POST /agent/shutdown` 注释中补充：

```python
POST /agent/shutdown           # 优雅关闭
                               #   同步阻塞直到关闭序列完成（Phase 5→0）后返回 HTTP 200 OK
                               #   可能耗时较长（等待排水超时 drain_timeout_sec + WAL 刷盘）
                               #   幂等性：如果 Agent 已经关闭或正在关闭中，返回 200 OK（空操作）
                               #   超时建议：调用者应设置大于 drain_timeout_sec + 30s 的客户端超时
```

- 风险清单新增 #57 项
