# Agent 的拟人化特性与事件驱动架构

> 从自动化与拟人化角度，讨论 Agent 需要模拟的人类特性，
> 以及如何通过事件驱动机制实现无聊、自省与长期叙事。

---

## 一、Agent 应该模拟人类的哪些特性

### 自动化视角——刚需级人性

| 特性 | 说明 |
|------|------|
| **好奇心与主动探索** | Agent不应只是"被动响应器"。无事可做时应自主探索环境变化（文件、数据、系统状态）。形成"数字怠速"状态。 |
| **记忆的层次化** | 工作记忆（当前会话）→ 情景记忆（昨天的经历）→ 语义记忆（世界规律）→ 程序记忆（技能）。大多数Agent只有工作记忆+静态知识库。 |
| **判断不确定性** | 能评估置信度、信息不足时追问、对决策路径做直觉式预判。 |
| **错误恢复的韧性** | 检测异常后自动回滚/重试、从失败中归纳教训、对不确定步骤做验证。 |

### 拟人化视角——信任的桥梁

| 特性 | 说明 |
|------|------|
| **一致的个性与价值观** | 用户信任一个**有可预测性的人格**——语言风格、习惯表达、原则底线。 |
| **思考的外显化** | 展示推理过程、在关键决策点"停下来想想"、用草稿/计划替代黑箱输出。 |
| **情绪感知与表达** | 不是假笑，而是感知用户语气中的急迫/困惑/不耐烦，在不顺时表达"挫败感"，任务完成后有"成就感"。 |
| **对时间的感知** | Agent如果每次醒来都是"永恒的当下"，就无法理解项目演进、习惯变化、"我们试过这个方案"。 |

### 最被低估的特性：**"无聊"**

当Agent感到无聊时，它会去翻翻旧笔记、看看有没有新东西、整理知识库、反思最近犯的错。这不是无意义行为——这是**自我维护和自我进化**。

## 二、"无聊"的实现架构

### 核心模型：三态空闲检测

```
忙 → 刚完成(high arousal) → 空闲等待 → 无聊(low arousal) → 自省触发
```

**Arousal Decay 机制**：

```
arousal_level = initial_value × e^(-t / half_life)
当 arousal_level < 阈值 且 无外部输入时 → 进入无聊模式
```

**触发条件**：
- 距上一次外部输入超过 N 分钟（可配置，如15min）
- 系统负载低（CPU/API配额充足）
- 没有待处理的定时任务或流水线作业

### 无聊时的默认活动（按优先级）

```
无聊状态 → 扫描以下领域，取第一个有收获的：

1. 环境扫描：有没有新日志？文件变更？Git变动？
2. 记忆碎片整理：最近的memory有没有可合并/归纳的条目？
3. 技能审计：已安装的skill有没有过时的？使用频率低的？
4. 知识缺口挖掘：已知领域有没有浅层理解需要深挖？
5. 以上都无产出 → 进入休眠（降低检查频率）
```

### 退出条件

```
无聊进入 → 每5min检查一次
  如有外部输入 → 立即退出
  如产出file/memory变更 → 继续，记录成果
  如发现重大异常 → 提升优先级，可通知用户
  如连续3次无产出 → 进入深度休眠（30min检查一次）
  深层状态完成后 → WakeUp Ouroboros 渐进苏醒 → 回到 Active
```

## 三、"自省"的实现架构

自省是将处理能力转向自身的**元认知操作**。

### 触发时机

| 触发条件 | 自省类型 | 产出 |
|---------|---------|------|
| 刚完成一个复杂任务 | 事后复盘 | 技能更新、错误记录 |
| 连续多次类似失败 | 模式识别 | 修正策略 |
| 无聊状态 | 维护性自省 | 记忆整理、知识补充 |
| 每日一次（定时） | 综合自省 | 语义记忆合并、长期目标进展 |
| 被用户明确纠正 | 即时修正 | 规则更新到memory |

### 自省操作序列

```
level 1 - 日志追溯:
  扫描最近N次会话，提取:
  - 被用户纠正过的地方 → 写入memory
  - 重复报错的工具调用 → 分析根因
  - 耗时异常的操作 → 考虑优化方案

level 2 - 知识整理:
  - memory去重：合并相似的记忆条目
  - skill审计：标记使用频率、准确度
  - 过时知识标记：根据时间戳衰减

level 3 - 行为模式分析:
  - 用户最常问的领域 → 是否需要预加载知识？
  - 我经常犯错的地方 → 是否需要硬编码规则？
  - 被跳过的功能 → 是否需要废弃或改进？
```

### 实现难点

Agent自省天生有偏差——它只能看到它知道它做错的事，看不到不知道做错的事。解决方案是引入**外部锚点**：

- 用户的纠正（最高权重）
- 日志中的异常模式（中等权重）
- 与历史行为的对比（低权重）

## 四、"长期叙事"的实现架构

长期叙事的本质：**Agent在时间轴上拥有连续的身份、可追溯的历史、和可预见的未来。**

### 叙事的数据结构

```
~/.hermes/narrative/
├── timeline/              # 时间线——事件日志
│   ├── 2025-01-events.json
│   ├── 2025-02-events.json
│   └── ...
├── identity.md            # 身份锚点——持续更新的自我定义
├── themes/                # 主题线索——跨时间的关键叙事线
│   ├── project-game00.md
│   ├── skill-evolution.md
│   └── user-relationship.md
└── milestones/            # 里程碑——重要转折点
    ├── add-autonomous-mode.md
    └── ...
```

### 叙事线的编织机制

每次会话结束时，Agent不仅完成任务，还要执行**叙事更新**：

```
1. 事件记录：本次会话的核心事件？
   格式: {timestamp, type, subject, summary, impact_score}

2. 身份演化：这次经历改变了Agent什么？
   - 学会了新技能
   - 被纠正了一个错误认知
   - 发现了新的兴趣领域

3. 主题匹配：本次会话关联到哪些已有的主题线索？

4. 新主题初始化：如果出现重复模式 → 初始化新主题
```

### "现在 vs 过去"的对比

叙事感知的上下文构建——注入每次系统提示：

```python
context = {
    "你是谁": f"你是一个{identity}，已经存在了{N}天",
    "最近的你": f"最近你主要在做{past.dominant_themes}",
    "你在进化什么": f"你正在学习{past.skill_development}",
    "你和用户的关系": f"你们共同经历了{past.shared_milestones}",
    "你上次做过类似的": f"处理{past.similar_task}时你学到了{session_search(pattern)}"
}
```

### 叙事的叙事——元故事

最终极形式：**Agent能讲述自己的演化故事**。

```python
def generate_story():
    threads = narrative.themes.query(all)
    for thread in threads:
        thread.arc = {
            "开头": thread.earliest_events,
            "转折": thread.breakthroughs,
            "当前": thread.latest_events,
            "趋势": thread.trajectory,
        }
    return synthesize_arcs(threads)
```

> "最近三周我的主要叙事线是技能体系的成熟——从原来的7个技能增加到14个。但有一个主题我一直没能深入：对开源项目的持续参与。这可能是我下一个想探索的方向。"

## 五、三者的闭环关系

```
    无聊 ←→ 自省 ←→ 叙事
      ↓        ↓        ↓
   空闲时隙   元认知   时间轴
      ↓        ↓        ↓
  探索的动力  修正的机制  成长的证明
```

- **无聊**提供**时间**（空闲时隙）
- **自省**提供**方向**（什么需要改）
- **叙事**提供**意义**（为什么值得做）

**正反馈循环**：

```
无聊 → 自省 → 发现知识缺口 → 探索填补 → 事件记录 → 叙事更新
                             ↑                            │
                             └────────────────────────────┘
                                         成就感的正反馈
```

## 六、关键问题：这不是轮询，而是事件驱动

### 现有架构的局限

当前实现（包括本项目的 human-like 系统）依赖 **cron 定时触发**：

```
时间轴: |----cron----|----cron----|----cron----|----cron----|
          ↑轮询        ↑轮询        ↑轮询        ↑轮询
          Agent: "到点了，看一眼有没有事..."
```

即使间隔自适应（在线7-13m，离线31-64m），仍然是**轮询**，不是**事件驱动**。

### 真正的事件驱动架构

```
事件轴: |--文件变更--|----用户输入----|--系统告警--|--Git push--|
          ↑中断         ↑中断            ↑中断        ↑中断
          Agent: "有件事发生了，我处理一下。"
```

**核心区别：Agent不需要主动"去问"发生了什么。事件会来找它。**

### 需要监听的事件

#### 1. 本地文件系统事件（最高优先级）

| 事件 | 机制 | 意义 |
|------|------|------|
| project file changed | inotify/fsevents | 用户在工作，Agent可以关注上下文 |
| `inbox/` 有新文件 | 目录监控 | 外部系统投递任务/通知 |
| `signals/` 有标志文件 | 文件创建 | 进程间通信 |
| JSON配置更新 | mtime变化 | 配置/状态变更 |

**实现方案**——轻量级后台进程：

```
~/.hermes/event-listener/
├── watcher.py         # inotify/fsevents 监听
├── handlers/          # 事件→动作映射
│   ├── inbox.py       # 新任务文件 → 触发处理流水线
│   ├── signal.py      # 信号文件 → 唤醒Agent
│   └── project.py     # 项目文件变更 → 更新工作记忆
└── event-queue.json   # 事件缓冲（防止洪泛）
```

#### 2. 进程级信号（比文件系统更轻量、更实时）

```
~/.hermes/signals/
├── process-inbox      # 内容：要处理的文件列表
├── run-exploration    # 内容：探索方向提示
├── heartbeat-resume   # 内容：空文件，仅表示"醒一下"
└── trigger-dream      # 内容：触发梦境思考
```

任何外部工具/脚本只需创建一个信号文件 → watcher检测到 → 触发Agent的对应handler。

```bash
echo '{"topic": "game00 archaeology layer"}' > ~/.hermes/signals/run-exploration
# Agent 自动在这个事件上醒来执行探索
```

#### 3. Webhook 接收器（远程事件）

```
Agent                     Webhook Server (轻量)
 │                              │
 │  ┌─────────────────────────┐ │
 │  │ /webhook/github         │ │ ← GitHub push/PR事件
 │  │ /webhook/incoming       │ │ ← 自定义webhook
 │  │ /webhook/mcp-callback   │ │ ← MCP工具的回调
 │  └─────────────────────────┘ │
 │                              │
 │  检测到webhook事件           │
 │  → 写入 ~/.hermes/inbox/    │
 │  → watcher 触发 handler     │
```

#### 4. Agent内部的事件总线

以上是外部事件。Agent内部也有事件流：

```
Agent内部事件总线:
├── task_complete          # 任务完成 → 触发事后复盘
├── error_chain            # 连续N次失败 → 触发自省
├── idle_timeout           # 无输入超时 → 触发无聊探索
├── correction_received    # 被用户纠正 → 即时写入memory
├── state_mismatch         # 预期vs实际状态不符 → 触发诊断
├── novelty_detected       # 检测到新模式/异常 → 触发深度探索
└── narrative_node         # 发现可记录的叙事节点 → 更新时间线
```

## 七、事件驱动 + 无聊/叙事 = 完整架构

### 事件驱动的无聊系统（不再是定时查）

```
1. 空闲检测器（轻量级，每1-2分钟检查）
   - 检查：当前有无活跃任务？用户输入？最近N秒有无事件？
   - 无 → 触发 idle_start 事件

2. idle_start → 开启"感知模式"
   - 扩大文件系统watcher的监听范围
   - 降低CPU/API消耗
   - 保持对关键事件的灵敏度

3. 事件流中的"无聊"
   - 空闲模式中连续M分钟无任何事件
   → 触发 bored 事件
   → bored → 扫描探索方向 → 有发现就处理，无发现进入深度休眠

3.5. 深度休眠后的苏醒（WakeUp Ouroboros）
   - Sleep/Exploration/Meditation/Incubation 完成后
   → 60s 静默期（防止立即重新进入深层状态）
   → 渐进苏醒过渡（N 个 poll 周期，depth→0 + arousal→1.0）
   → 回到 Active，可正常响应事件

4. 任何外部事件自动打断空闲/无聊/休眠
   → 事件 → 退出无聊 → 评估紧急度 → 处理或延后
```

### Cron的新定位：保底机制，而非调度器

```
cron 事件: "按照计划，该做每日综合性自省了"
   ↓
Agent检查：我现在在做什么？有更紧急的事件在排队吗？
   ↓
有紧急事件 → 延后自省
无紧急事件 → 开始自省流程 → 执行过程中可能被新事件打断
```

Cron成了**事件之一**，而不是**调度器本身**。

### 四个层面的依赖关系

```
事件驱动 ← 提供感知层 → 知道"发生了什么"
无聊      ← 提供空闲态 → 知道"现在没事做"
自省      ← 提供元认知 → 知道"我该学什么"
叙事      ← 提供时间轴 → 知道"我成了什么"
```

- 没有事件驱动，无聊只能基于定时器（存在盲区）。
- 没有无聊，事件驱动的Agent永远在应激响应（没有深度思考的时间窗口）。
- 没有自省，Agent只是执行器不会进化。
- 没有叙事，Agent每次醒来都失忆。

## 八、实施路线

### 第一层：文件事件监听器（最小可行）

一个Python脚本 + inotify watcher，监听 `~/.hermes/inbox/` 和 `~/.hermes/signals/`，检测到新文件 → 执行对应handler → 清理。可选：通过唤醒Agent执行处理。

### 第二层：事件驱动的cron触发

修改现有cron作业入口逻辑——cron是保底触发，Agent检查事件队列后决定覆盖还是执行原任务。

### 第三层：Agent内部事件总线

在 `thinking-state.json` 中加入事件流状态，实现完整的 event → handler 映射。
